# Runtime parity: decisions

agentd's runtime matches Anthropic Managed Agents feature for feature: the agent loop runs in agentd, and workers
running Anthropic's own worker live outside agentd ([ADR 0001](adr/0001-agent-loop-in-agentd.md)). "Live" means
Anthropic's hosted Managed Agents API. Each row names who decided and when.

## Architecture

| # | Decision | Source |
|---|---|---|
| D1 | The agent loop runs in agentd, server side. | User, 2026-11-05 and 2026-11-08 ("must match anthropic feature for feature") |
| D2 | Workers run the official SDK's `EnvironmentWorker` unchanged, started per work item through its documented entry `worker(workdir="/workspace").handle_item()`. | User, 2026-11-08 |

| D6 | The worker image, its Docker and Fargate launchers, the file sidecar and the egress proxy with placeholders are a separate container project, `agentd-worker`, in its own repository, speaking only the public API, so it runs against live as well as agentd. | User, 2026-11-08 (name chosen the same day) |

## The loop at scale

| # | Decision | Source |
|---|---|---|
| D8 | No session state in a replica's memory. The event log in Postgres is the state; a step reads it, builds the prompt, calls the model, and appends its events in one commit. A crash repeats at most one step, which is safe to repeat, except a step that called an MCP tool, which may call it again (an accepted risk, MC-25). | User, 2026-11-08 ("okay. lets do that") |
| D9 | Steps come from a queue. A session joins it when a client event, `user.tool_result` or `user.custom_tool_result` arrives, and stays on it when its step leaves an allowed MCP call for the next step (MC-24); a loop worker claims it with `FOR UPDATE SKIP LOCKED` under a lease with an expiry, runs one step and releases it. Nothing is held while a tool runs. No subqueries. | User, 2026-11-08 |
| D10 | One binary, two roles: the API (requests and streams) and loop workers (steps). The role is a setting; each scales on its own, loop workers on queue depth. | User, 2026-11-08 |
| D11 | Model provider limits: a per-workspace concurrency limit, retries with backoff on 408, 409, 429 and 5xx in the model client only, prompt caching where the provider supports it; each value a setting per deployment environment. | User, 2026-11-08 |
| D12 | Scheduled jobs work with more than one replica: schedule changes reach the scheduler through an outbox (D50), the built-in scheduler keeps schedules in Postgres and one replica claims each due fire, and every fire passes the fire inbox. | User, 2026-11-08; the outbox, D50 |
| D13 | Model limit defaults: 32 concurrent model calls per workspace, 5 attempts from 2 s with jitter inside a 10 min deadline, `cache_control` on the system prompt and tool list for Anthropic models. | User, 2026-11-08 (plan approved) |

## The loop's context and MCP

| # | Decision | Source |
|---|---|---|
| D31 | Compaction per thread, in two tiers. Tier 1 clears old tool results from the prompt at the lower of `compaction.clear_at` (default 100,000 tokens) and 50% of the model's window, keeping the last 3 results (a setting from 3 to 5), every tool input and every error, each cleared result leaving a placeholder naming its event id. Tier 2 summarises at 80% of the model's window, with no fixed cap. The window comes from the model's provider list (D42). The prompt size is estimated from the previous model call's usage plus an estimate of the new events, with no counting call. Compaction is a step of its own from the same queue, only between turns with no tool call waiting, at most one per thread. A summary builds on the previous checkpoint and the events after it, keeps the user's messages verbatim up to about 20,000 tokens (for Anthropic models, as many as fit the 16,384-character `instructions` limit, C1) and the last turns, and covers the goal, constraints, decisions, files touched, open todos, unresolved errors and next steps. Anthropic models use on-demand compaction (`compact-2026-09-04`), the block sent back unmodified; other models use a handoff prompt like Codex's. The checkpoint is the `agent.thread_context_compacted` event, recording the last event it covers and the model that wrote it, unique per thread and position. Compaction deletes no event. A tool output is capped (`tool_output_token_limit`) when the loop appends it to the prompt. | User, 2026-11-08 ("do it"; the summary point: "No cap", "80% then") |
| D32 | MCP caches: the MCP session id (`Mcp-Session-Id`) and the tool list are kept per agentd session and server in Postgres, never in memory and never shared across sessions or workspaces. The loop reconnects when the server answers 404 or when the credential changes; a turn's start keeps each open connection and retries only the servers whose connection failed, as live does (B27). It refreshes the tool list on `notifications/tools/list_changed` or a reconnect. A credential is read only in a step that connects or calls a tool on its server (D27). | User, 2026-11-08 ("do it"); a turn's start, live's B27 capture, 2026-11-15 |
