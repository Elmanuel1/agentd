# Runtime parity: decisions

agentd's runtime matches Anthropic Managed Agents feature for feature: the agent loop runs in agentd, and workers
running Anthropic's own worker live outside agentd ([ADR 0001](adr/0001-agent-loop-in-agentd.md)). "Live" means
Anthropic's hosted Managed Agents API. Each row names who decided and when.

## Architecture

| # | Decision | Source |
|---|---|---|
| D1 | The agent loop runs in agentd, server side. | User, 2026-11-05 and 2026-11-08 ("must match anthropic feature for feature") |
| D2 | Workers run the official SDK's `EnvironmentWorker` unchanged, started per work item through its documented entry `worker(workdir="/workspace").handle_item()`. | User, 2026-11-08 |
| D3 | agentd serves only the endpoints and event types live serves; no agentd-only route and no endpoint live does not have. | User, 2026-11-06 and 2026-11-08 |
| D4 | Custom tools are answered by the sessions API caller (`user.custom_tool_result`); workers run the built-in toolset only, as they do by default. | User, 2026-11-04 |
| D5 | agentd is the API, the loop and the work queue. It holds no container code: no launcher, no runtime adapter, no sidecars, no dispatcher, no file staging, no snapshots, no egress proxy. | User, 2026-11-08 ("This self container implementation is not for agentd ... don't mix it together") |
| D6 | The worker image, its Docker and Fargate launchers, the file sidecar and the egress proxy with placeholders are a separate container project, `agentd-worker`, in its own repository, speaking only the public API, so it runs against live as well as agentd. | User, 2026-11-08 (name chosen the same day) |
| D7 | `cloud` environments are served by our own deployment of the container project: its workers poll agentd's runtime queue with our environment key, as a customer's workers poll their environment. `cloud` and `self_hosted` differ only in who runs the workers and holds the key. | User, 2026-11-08 ("We can reuse our self host as the cloud right": yes) |

## The loop at scale

| # | Decision | Source |
|---|---|---|
| D8 | No session state in a replica's memory. The event log in Postgres is the state; a step reads it, builds the prompt, calls the model, and appends its events in one commit. A crash repeats at most one step, which is safe to repeat, except a step that called an MCP tool, which may call it again (an accepted risk, MC-25). | User, 2026-11-08 ("okay. lets do that") |
| D9 | Steps come from a queue. A session joins it when a client event, `user.tool_result` or `user.custom_tool_result` arrives, and stays on it when its step leaves an allowed MCP call for the next step (MC-24); a loop worker claims it with `FOR UPDATE SKIP LOCKED` under a lease with an expiry, runs one step and releases it. Nothing is held while a tool runs. No subqueries. | User, 2026-11-08 |
| D10 | One binary, two roles: the API (requests and streams) and loop workers (steps). The role is a setting; each scales on its own, loop workers on queue depth. | User, 2026-11-08 |
| D11 | Model provider limits: a per-workspace concurrency limit, retries with backoff on 408, 409, 429 and 5xx in the model client only, prompt caching where the provider supports it; each value a setting per deployment environment. | User, 2026-11-08 |
| D12 | Scheduled jobs work with more than one replica: schedules live in Postgres and one replica claims each due fire. | User, 2026-11-08 |
| D13 | Model limit defaults: 32 concurrent model calls per workspace, 5 attempts from 2 s with jitter inside a 10 min deadline, `cache_control` on the system prompt and tool list for Anthropic models. | User, 2026-11-08 (plan approved) |

| D18 | The event log stays on Postgres behind its port, with no partitioning; DynamoDB for large workspaces is the scale-up step behind the same port, planned when its trigger fires (SRE). | User, 2026-11-06; Postgres for now, user, 2026-11-08 ("Yeah. Postgres for now") |
| D19 | The work secret carries live's keys and values. | User, 2026-11-06 |
| D20 | Session webhook endpoints are registered through agentd configuration per organization, since live registers them only in its Console; deliveries follow live exactly. | User, 2026-11-08 (plan approved) |
| D21 | Starter SLOs as signed off on 2026-11-06, targets in one config file. | User, 2026-11-06 |
| D22 | No paid model run without the user's OK; CI uses the scripted model. | User, standing |
| D23 | Each PR in [requirements](requirements.md) starts on the user's go-ahead; the `agentd-worker` repository is created on the user's go-ahead. | User, 2026-11-08 |
| D24 | A session's work token may read its session's mounted files through `GET /v1/files/{id}/content` and save outputs through `files.upload`, scoped to that session so `files.list(scope_id=session)` returns them; any other session's file, and a file not mounted in the session, are refused. No new route. Live refuses this; it departs from live because agentd holds no container code (D5) and `agentd-worker` speaks only the public API (D6), so its sidecar can stage files only through the files endpoints. | User, 2026-11-08 ("Yes") |
| D25 | Our `cloud` deployment of `agentd-worker` substitutes `environment_variable` credentials at egress, as live's `cloud` sandboxes do: the sandbox holds only placeholders and the real value is attached outside it, only for the credential's allowed hosts. `self_hosted` sessions get no substitution and no placeholders, as on live. On the Cloudflare launcher the session's Durable Object does the swap in its outbound handler (D38); on the optional Fargate and EC2 launchers a separate egress proxy does it, with its own IAM role allowed only `secretsmanager:GetSecretValue` on secrets tagged `credential_type=environment_variable` and on `<prefix>/system/egress_key`, and `kms:Decrypt` through Secrets Manager; the sandbox task role holds nothing. A swap refuses the request when it cannot read the value. No value reaches the sandbox, an event, a log or an output. For any other operator of `agentd-worker`, secret injection stays optional and off by default. The model key never leaves agentd. | User, 2026-11-08 ("it must match"; "Env variables don't work in self hosted") |
| D26 | The loop serves the agent's MCP servers for every environment type, with credentials from the session's vaults as Anthropic picks them. | User, 2026-11-08 |
| D27 | The loop reads each MCP credential once per loop step, not per request; a rotated or revoked credential applies from the next step. Why: 2 to 3 times fewer Secrets Manager reads, the secret held a few seconds in memory inside agentd only, and large multi-tenant systems cache credentials for minutes. | User, 2026-11-08 ("Go ahead") |
| D28 | agentd hands `agentd-worker` a session's environment-variable credentials through the work secret the worker already receives, with no new route (D3): for a `cloud` session, its `environment_variables` key (B2) maps each credential's `secret_name` to a placeholder; for a `self_hosted` session it is empty. A placeholder is signed by agentd with `<prefix>/system/egress_key` over the session, workspace, vault and credential ids, so one copied into another session is never substituted. The swap learns the allowed hosts and injection location from the credential's sealed secret, which already holds `networking` and `injection_location` beside the value: the AWS egress proxy reads it per request (EG-6) and the Cloudflare Durable Object keeps it at most 5 minutes (D38, CF-6); the Fargate and EC2 proxy learns the calling session from `Proxy-Authorization: Basic <session id>:<sessions_token>`, checked with `GET /v1/sessions/{id}` (A3); on Cloudflare the Durable Object belongs to one session, so a placeholder for any other session is never substituted. A placeholder the swap does not substitute is sent unchanged, as live sends it (B28). | User, 2026-11-08 ("it must match"); the parent session's brief: no agentd-only route; Anthropic's vaults page, read 2026-11-09, for unsubstituted placeholders (B28) |
| D29 | Vault behaviour follows Anthropic's docs (B15 to B18): a session's `vault_ids` is fixed at creation and an update that sets it is refused; archiving a vault archives its credentials and purges their secrets, so running sessions keep running without them (MCP credentials from their next step, `environment_variable` values within 5 minutes on Cloudflare) and new sessions that reference it are refused; rotating, archiving or deleting a credential applies to running sessions at their next loop step for MCP credentials and within 5 minutes on Cloudflare for `environment_variable` credentials; `token_endpoint` cannot change; an update with a new `access_token` and no `expires_at` keeps the old expiry; `mcp_oauth_validate` answers `valid`, `invalid` or `unknown`. | User, 2026-11-08 ("do it"); Anthropic's vaults page, read 2026-11-09, for the archive cascade (B16) |
| D30 | One credential store for now: MCP and `environment_variable` credentials stay one Secrets Manager entry each, read through agentd's `SecretStore` and `agentd-worker`'s credential source. Envelope encryption (credentials sealed in Postgres under a KMS key per workspace, data keys cached briefly) is the scale-up path behind those same interfaces, for both kinds together, and starts when Secrets Manager reads pass 50% of the regional `GetSecretValue` limit (SRE section). | User, 2026-11-08 ("one store for now") |

## The loop's context and MCP

| # | Decision | Source |
|---|---|---|
| D31 | Compaction per thread, in two tiers. Tier 1 clears old tool results from the prompt at the lower of `compaction.clear_at` (default 100,000 tokens) and 50% of the model's window, keeping the last 3 results (a setting from 3 to 5), every tool input and every error, each cleared result leaving a placeholder naming its event id. Tier 2 summarises at 80% of the model's window, with no fixed cap. The window is the model's `max_input_tokens`. The prompt size is estimated from the previous model call's usage plus an estimate of the new events, with no counting call. Compaction is a step of its own from the same queue, only between turns with no tool call waiting, at most one per thread. A summary builds on the previous checkpoint and the events after it, keeps the user's messages verbatim up to about 20,000 tokens and the last turns, and covers the goal, constraints, decisions, files touched, open todos, unresolved errors and next steps. Anthropic models use on-demand compaction (`compact-2026-09-04`), the block sent back unmodified; other models use a handoff prompt like Codex's. The checkpoint is the `agent.thread_context_compacted` event, recording the last event it covers and the model that wrote it, unique per thread and position. Compaction deletes no event. A tool output is capped (`tool_output_token_limit`) when the loop appends it to the prompt. | User, 2026-11-08 ("do it"; the summary point: "No cap", "80% then") |
| D32 | MCP caches: the MCP session id (`Mcp-Session-Id`) and the tool list are kept per agentd session and server in Postgres, never in memory and never shared across sessions or workspaces. The loop reconnects when the server answers 404, when the credential changes, and on the idle-to-running transition, and refreshes the tool list on `notifications/tools/list_changed` or a reconnect. A credential is read only in a step that connects or calls a tool on its server (D27). | User, 2026-11-08 ("do it") |

## Deployment and scale

| # | Decision | Source |
|---|---|---|
| D33 | The Fargate launcher's fleet scales on the work queue: identical tasks, each polling for one work item, serving that session and exiting, so no container serves two sessions or tenants. A small job publishes `GET /v1/environments/{env}/work/stats` (queued plus active, plus a warm buffer, a setting, 0 at launch) per running task as a CloudWatch metric, and target tracking holds it at 1, with the job setting the desired count itself while no task runs; a busy task sets ECS task scale-in protection and clears it when done. Loop workers scale on the step queue's depth. Fargate vCPU and ENI quota increases are agreed with AWS before production volume. | User, 2026-11-08 ("do it"); the per-task metric, from the CodeRabbit review of 2026-11-09 |
| D34 | The launch deployment is lean: agentd runs as one container in the `all` role on tosspaper's existing host or ECS, behind the existing load balancer and NAT, with its own schema in tosspaper's Postgres, tosspaper's Valkey for pub/sub, and the existing S3 bucket, logs and metrics. No warm pool. Our `cloud` sandboxes run on Cloudflare Containers (D38). The full setup (its own RDS with RDS Proxy, separate role services, a Fargate fleet with a warm pool) is the scale-up path, and every switch between the two is a setting. | User, 2026-11-08 ("do it") |
| D35 | Scaling fixes at the sizing peak of 10^4 sessions: no RDS Proxy at launch, agentd's own pool of 10 to 20 connections, and RDS Proxy (transaction pooling) added when sustained connections pass 70% of `max_connections` or loop workers outgrow the pool; 256 steps per loop worker (a setting); an account-wide model limiter (requests and input tokens per minute) in Valkey beside the per-workspace limit, deferring a step when full rather than retrying into the limit; an optional event retention period; DynamoDB for large workspaces (D18); tuned autovacuum on `loop_steps`; a read replica for `events.list`; streams refused with `overloaded_error` while Postgres is overloaded. | User, 2026-11-08 ("do it"; "no rds proxy for now", "when we need to scale") |
| D36 | A Java SDK conformance suite (`com.anthropic:anthropic-java` 2.52.0) runs in CI beside the Python and TypeScript suites, with only the base URL changed. | User, 2026-11-08 ("do it") |
| D37 | The Java SDK's tunnels and user profiles services are out of scope for this plan; each gets its own parity plan next. Why: they are new resource families with their own tables and routes, not part of the runtime. | User, 2026-11-08 ("Out of scope, own plan") |
| D38 | Our `cloud` sandboxes run on Cloudflare Containers through a Cloudflare launcher in `agentd-worker`, built on Cloudflare's open-source `@cloudflare/containers` and `@cloudflare/sandbox`: one container per session, addressed by its session id through its Durable Object, running the official `EnvironmentWorker` unchanged, no warm pool, a fresh disk each start. `enableInternet = false` and `allowedHosts` enforce `limited` networking. The session's Durable Object holds the secrets and the container only placeholders: its outbound handler reads each value from Secrets Manager with one narrowly scoped AWS read key held as a Worker secret, caches it in the object's memory for 5 minutes (never in Durable Object storage, dropped on eviction and at session end), and fails closed when Secrets Manager cannot be reached and the cached value has expired. A rotated, archived or deleted credential applies within 5 minutes. agentd pushes nothing to Cloudflare and stays unaware of `agentd-worker`. agentd stays on AWS. The Docker launcher stays for development and CI; Fargate and EC2 stay optional for AWS-only operators. The launcher takes from Cloudflare's MIT template `claude-managed-agents` (G9), credited: the per-session sandbox Durable Object, the outbound-handler egress hook and R2 backups of `/workspace`. It differs where the template departs from live: while the container runs, the official `EnvironmentWorker` is the only process that heartbeats, stops or answers the work item; the environment key never enters the container; egress is deny by default and fails closed; values are swapped for placeholders (D28) from Secrets Manager, not injected from Workers KV; skills, memory stores and files come from the official worker and the files endpoints (D24). | User, 2026-11-08 ("use Cloudflare Containers for our cloud sandboxes"; "should cache and invalidate on change. Can invalidate every 5min?") |
| D39 | agentd's own runtime key (W-14) may call `GET /v1/environments/{id}` for an environment with a work item on the runtime queue, so the Cloudflare launcher can apply that environment's networking. It is a permission on an existing route, not a new route; every other environment key, and the runtime key for any other environment, keeps live's 403. The launcher caches the networking briefly (a setting) and applies it when a container starts; if the read fails, no container starts and the work item is stopped. | User, 2026-11-08 ("1") |
